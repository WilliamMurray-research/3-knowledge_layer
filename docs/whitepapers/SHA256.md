# SHA‑256 in the Knowledge Layer: Deterministic Hashing for Semantic Stability, Provenance Integrity, and Corpus‑Scale Synchronization  

## Abstract  
SHA‑256 plays a foundational role in Project 3.0 — the Knowledge Layer — by providing deterministic hashing for document identity, metadata stability, provenance tracking, and sync‑engine correctness. This whitepaper presents the cryptographic, architectural, and operational functions of SHA‑256 within the dual‑layer system (PostgreSQL + Memgraph), explains how hashing governs corpus‑scale metadata extraction, and defines the invariants required for reproducible sync cycles across 9,500+ research artefacts.

---

## 1. Introduction  
The Knowledge Layer is a dual‑layer semantic indexing system that synchronizes:

- PostgreSQL (canonical metadata)  
- Memgraph (dependency graph)  
- Local SLM (offline metadata extraction)  
- Local Git (provenance substrate)

To maintain deterministic behaviour across thousands of documents, the system requires a stable, collision‑resistant hashing mechanism. SHA‑256 provides this stability.

In your architecture, SHA‑256 is not merely a cryptographic primitive — it is a semantic invariant, a provenance anchor, and a governance constraint.

## 2. Why SHA‑256 Is Required in Project 3.0  

### 2.1 Deterministic Document Identity  
Every README.md, metadata block, and dependency list must be uniquely and reproducibly identified.

SHA‑256 ensures:

- identical content → identical hash  
- changed content → changed hash  
- no collisions in practice  
- stable identity across sync cycles  

This is essential for your offline SLM pipeline, which must only run when content changes.

### 2.2 Provenance Tracking  
Local Git uses SHA‑256 to anchor commit lineage.

In Project 3.0, SHA‑256 is used to:

- detect changes  
- log provenance events  
- maintain deterministic commit graphs  
- ensure reproducibility of research artefacts  

### 2.3 Sync Engine Efficiency
Your Bash sync engine must avoid unnecessary SLM calls.

SHA‑256 enables:

- content hashing  
- metadata hashing  
- dependency hashing  

If the hash matches the previous sync, the engine skips extraction.

### 2.4 Corpus‑Scale Stability  
With 9,500+ documents, nondeterministic behaviour is unacceptable.

SHA‑256 provides:

- stable identity  
- stable lineage  
- stable dependency resolution  
- stable metadata caching

## 3. Cryptographic Properties Relevant to Project 3.0  

### 3.1 Collision Resistance  
Two different documents will not produce the same hash.

This ensures:

- safe indexing  
- safe provenance  
- safe dependency mapping  

### 3.2 Preimage Resistance  
Given a hash, it is computationally infeasible to reconstruct the document.

This protects:

- proprietary documents  
- restricted UOA corpus  
- sensitive metadata  

### 3.3 Determinism  
SHA‑256 always produces the same output for the same input.

This is the most important property for your sync engine.

## 4. SHA‑256 in the Knowledge Layer Architecture  

### 4.1 Hashing README.md Content  
Each project’s README.md is hashed before SLM extraction.

Stored in PostgreSQL:

| Field | Purpose |
|-------|---------|
| slm_hash | Detect content changes |
| dependsonhash | Detect dependency changes |
| metadata_hash | Detect metadata drift |

### 4.2 Hashing SLM Output  
The SLM returns:

- title  
- description  
- tags[]  
- depends_on[]  

This JSON is hashed to detect semantic drift.

### 4.3 Hashing Dependency Lists    
Memgraph edges are only updated when the dependency hash changes.

### 4.4 Hashing Provenance Events  
Local Git commit metadata includes SHA‑256 of:

- staged artefacts  
- metadata blocks  
- environment fingerprints  

This creates a deterministic provenance chain.

## 5. SHA‑256 in the Sync Protocol  

Step 1 — Hash README.md
If unchanged → skip SLM.

Step 2 — Hash SLM Output
If unchanged → skip PostgreSQL update.

Step 3 — Hash Dependency List
If unchanged → skip Memgraph update.

Step 4 — Hash Provenance Event
Local Git logs the event only when content changes.

Step 5 — Insert Hashes into PostgreSQL
This forms the canonical identity substrate.
